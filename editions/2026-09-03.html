Null Bytes and AMSI: A Parsing Bug That Bypasses Windows Defender

Satoshi Tanda disclosed a critical AMSI bypass that exploits how PowerShell's System.Management.Automation.dll forwards script contents to AMSI providers. By inserting a null character before malicious code, the module truncates the content at that byte—a parsing difference between AmsiScanString (which treats null as a string terminator) and AmsiScanBuffer (which doesn't). This allowed detection-free execution of tools like Invoke-Mimikatz on patched systems and works even in Constrained Language Mode without triggering event logs.

This is textbook implant evasion tradecraft: understanding AMSI's design seams and how to slip payload execution past signature scanning. The technique demonstrates why you need to know the difference between how APIs are *supposed* to work and how they're actually implemented—Microsoft fixed it with a single API swap, but the research model is pure offensive: find the gap, measure the bypass, document the fix.

Heaven's Gate Closed: CFG and WoW64 Isolation on Windows 10

Alex Ionescu detailed how Control Flow Guard on Windows 10 uses separate CFG bitmaps for 32-bit and 64-bit code, keyed by address range rather than execution mode. Since WoW64 processes can't allocate above 4GB, and the 64-bit bitmap only validates calls within those addresses, naked 64-bit code executing in a WoW64 context will instantly fail CFG checks. The architecture forces a binary choice: 32-bit code below 4GB or legitimate 64-bit code above it—eliminating the Heaven's Gate technique that once let malware bypass EMET and AV hooks.

This is a direct result of Microsoft's response to old red-team tactics. Understanding *how* they closed the gate—through bitmap isolation and address-space partitioning—teaches you why naive implant evasion won't work on modern systems and what the real mitigations actually prevent. CFG design is part of your baseline OS security model.

RegPwn: Accessibility Feature EoP via Registry Symbolic Links

MDSec disclosed a Windows 10/11 EoP vulnerability (CVE-2026-24291) where accessibility features (on-screen keyboard, narrator) execute as SYSTEM and read/write registry keys that are user-controlled. By placing an opportunistic lock on a file to delay osk.exe startup, an attacker could replace the registry key with a symbolic link, achieving arbitrary registry writes as SYSTEM. The technique led to privilege escalation via service binary patching.

This is a complete end-to-end EoP chain using Windows-specific primitives (opportunistic locks, registry links, service control). The methodology—registry race conditions, timing attacks, SYSTEM-context code paths—is classic red-team reconnaissance applied to a built-in Windows component. Study how they identified the codepath, timed the exploit, and weaponized the primitive.

Extracting UEFI Runtime Drivers from Windows via HalEfiRuntimeServicesBlock

Satoshi Tanda's kraft_dinner tool demonstrates extracting UEFI runtime driver addresses from Windows by locating HalEfiRuntimeServicesBlock (accessible via HalQuerySystemInformation on older Windows, harder on 19H2+). The tool explores limitations: only drivers implementing runtime services are found, and memory-scanning approaches face obstacles with MmCopyMemory.

Runtime drivers are invisible to standard Windows monitoring tools. Understanding how to find and dump them is useful for supply-chain security research and for analyzing OEM-specific persistence mechanisms (like Absolute's Computrace module, which installs via WPBT ACPI tables set from firmware).
